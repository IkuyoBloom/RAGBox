# 向量数据库与近似最近邻检索

## 一、为什么需要专门的向量数据库

稠密向量检索的核心操作是「给定查询向量，在 N 个向量中找出最相似的 K 个」。
最朴素的实现是暴力搜索（Brute-force / Flat 索引）：逐一计算查询向量与库中
每个向量的距离，排序后取前 K。

暴力搜索的召回率是 100%（即精确最近邻），时间复杂度为 O(N·d)，
其中 d 是向量维度。当 N 达到百万级、d 为 768 或 1024 时，
单次查询需要数亿次浮点运算，无法满足在线服务的延迟要求。

近似最近邻（Approximate Nearest Neighbor, ANN）检索通过牺牲少量召回率，
把复杂度降到亚线性，这是向量数据库存在的前提。

## 二、相似度度量

三种常用度量及其适用场景：

- **余弦相似度**：衡量向量方向的夹角，对向量模长不敏感。
  文本检索中最常用，因为文档长度不应影响语义相似度判断。
- **内积**：同时受方向与模长影响。若向量已归一化，内积与余弦等价。
- **欧氏距离**：衡量空间中的绝对距离，对模长敏感。

工程上的一个常见陷阱：多数向量库默认使用欧氏距离或内积，
若把未归一化的文本向量直接入库并期望「余弦相似度」的排序，
结果会与预期不符。使用前必须显式确认索引的度量空间配置。

## 三、主流索引结构

### 3.1 HNSW（Hierarchical Navigable Small World）

HNSW 构建多层图结构：底层包含全部节点，上层是逐层稀疏的「高速公路」。
检索时从顶层入口点出发，贪心地向更近的邻居移动，到达局部最优后下降到下一层，
最终在底层精确定位。

关键参数：

- `M`：每个节点的最大连接数。越大召回率越高，但内存占用与构建时间上升。
  常用取值 16 至 48。
- `efConstruction`：构建期的候选队列大小。越大索引质量越好，构建越慢。
- `efSearch`：查询期的候选队列大小。**这是检索时唯一可以调节的精度/速度旋钮**，
  调大则召回率上升、延迟增加。

HNSW 的优点是查询速度快、召回率高，且支持增量插入；
缺点是内存占用大（图结构本身需要额外存储），构建时间较长。

### 3.2 IVF（Inverted File Index）

IVF 先用 k-means 把向量空间划分为若干簇（对应参数 `nlist`），
检索时只访问与查询向量最近的 `nprobe` 个簇，从而减少计算量。

`nprobe` 越大召回率越高但越慢。IVF 的内存占用比 HNSW 小，
但需要预先训练聚类中心，且对数据分布变化较敏感。

### 3.3 PQ（Product Quantization）

PQ 把高维向量切分成若干子段，对每个子段分别做聚类，
用聚类中心的编号代替原始浮点数值，从而大幅压缩存储。

例如一个 1024 维的 float32 向量占 4096 字节；
若切成 64 段、每段用 8 位编码表示 256 个聚类中心，则只需 64 字节，
压缩比达到 64 倍。代价是量化误差导致召回率下降，
通常需要配合重排序（用原始向量对候选集精算）来弥补。

### 3.4 组合方案

实践中常将上述方法组合，例如 **IVF-PQ**（先粗聚类再量化压缩）
或 **HNSW-PQ**。选择依据主要是三个约束的权衡：
召回率要求、内存预算、构建与查询的延迟预算。

## 四、过滤检索的两种模式

带元数据过滤的向量检索（例如「只在某个知识库内检索」）有两种实现：

- **后过滤（Post-filtering）**：先做 ANN 检索取 Top-K，再按条件过滤。
  实现简单，但当过滤条件选择性很强时，过滤后可能剩余结果过少，
  需要反复扩大 K 重试。
- **前过滤（Pre-filtering）**：先按条件筛出候选集，再在候选集内做 ANN。
  召回率有保障，但若候选集很大则退化为暴力搜索，
  且不少索引结构对动态过滤的支持有限。

多知识库隔离场景下，更稳妥的做法是**每个知识库使用独立的 collection**，
从根上避免过滤带来的召回损失 —— 这也是本项目采用的做法。

## 五、持久化与一致性

向量库与关系库并存时，一致性问题无法回避。常见方案有三：

1. **以关系库为准，向量库可重建**：文本与元数据存关系库，
   向量库只存向量与主键映射。两者不一致时重建向量索引即可。
   实现简单，是本项目采用的方案。
2. **分布式事务**：代价高，且多数向量库不支持事务语义。
3. **写前日志 + 补偿任务**：工程复杂度最高，适用于超大规模场景。

关键原则是：**必须明确哪一侧是唯一事实来源**，
否则出现不一致时无从判断该以谁为准。
